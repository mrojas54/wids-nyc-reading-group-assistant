# WiDS NYC AI Reading Group — Member App Design

**Date:** 2026-05-03
**Status:** Approved (pending final review)
**Companion to:** [2026-05-03-wids-nyc-reading-group-design.md](./2026-05-03-wids-nyc-reading-group-design.md)

## 1. Overview

The existing WiDS NYC AI Reading Group system is operator-side only: slash commands (`/wids-meeting-start`, `/wids-make-guide`, etc.) and scheduled tasks against a Supabase database. Members interact with the system today via email, Google Calendar invites, and a recurring Google Form for monthly availability.

This spec adds the first **member-facing surface**: a Next.js web app on Vercel with three jobs.

### Goals

1. **Submit availability** for the next admin or reading_group meeting that's in planning. Replaces the Google Form.
2. **Member status dashboard** — read-only view of the current cycle from the member's perspective: next meeting, their submission state, their history. Includes a fallback RSVP control for scheduled meetings.
3. **Per-paper study companion** — a public, static, paper-specific webpage with a section-by-section walkthrough (Mermaid diagrams + matching tiny Colab notebook cells). Generated by a new operator slash command.

### Non-goals (v1)

- Push notifications
- Mobile native app (the web app is mobile-first responsive; that's enough)
- Comment threads or member-to-member messaging
- Search across past papers / meeting notes archive
- Companion page versioning (git history is the version history)
- Member-editable profile (name/email change — operator handles via DB)
- Bidirectional calendar sync (portal RSVP → Google Calendar invite write-back)
- A test framework / CI pipeline (manual smoke tests are sufficient for ~10 members)

## 2. System Shape

Two surfaces, **one** Next.js 14 App Router app, **one** Vercel deploy, **one** domain.

```
                  ┌──────────────────────────────────┐
                  │   Next.js app on Vercel          │
                  │                                  │
  member ──email──┤  /                  (sign in)    │
                  │  /auth/callback     (magic link) │
                  │  /dashboard         (auth req'd) │
                  │  /availability      (auth req'd) │
                  │  /papers/<id>       (PUBLIC)     │
                  └──────────┬───────────────────────┘
                             │
                  ┌──────────▼───────────────────────┐
                  │   Supabase                       │
                  │   - auth.users (magic link)      │
                  │   - members (existing) + auth_id │
                  │   - availability, meetings,      │
                  │     papers, meeting_attendance   │
                  │   - RLS: members read/write own  │
                  └──────────────────────────────────┘

  operator ── /wids-make-companion ── reads paper PDF ── writes to repo:
                                       /content/papers/<id>.json (sections)
                                       /public/notebooks/<id>.ipynb
                                      ── git commit + push ── Vercel rebuilds
                                      ── /papers/<id> renders the new page
```

### Key boundary decisions

- **Auth boundary at the route level.** `/dashboard` and `/availability` require a Supabase session. `/papers/<id>` is public (so members can share, and so the email packets can deep-link).
- **Companion content as repo files, not DB rows.** Each paper has a JSON content file (`/content/papers/<id>.json`) and a notebook (`/public/notebooks/<id>.ipynb`). Companions are git-tracked, regenerate-able idempotently, statically rendered by Vercel — no DB queries on companion page load.
- **Notebook public via GitHub.** "Open in Colab" links to `colab.research.google.com/github/<owner>/<repo>/blob/main/public/notebooks/<id>.ipynb`. Notebook lives in the same repo. No separate notebook storage.
- **Slash command writes to local filesystem then commits.** `/wids-make-companion` follows the existing claude-code pattern — read paper PDF, dispatch subagent for sections+code, write files, ask operator to review the diff, then `git commit && git push`. Vercel auto-deploys on push.

## 3. Schema Changes

New migration `migrations/002_member_app.sql`. Two additive ALTER TABLEs, no destructive edits.

### 3.1 Link `members` to Supabase Auth

```sql
ALTER TABLE members ADD COLUMN auth_user_id UUID REFERENCES auth.users(id) ON DELETE SET NULL;
CREATE UNIQUE INDEX members_auth_user_id_idx ON members(auth_user_id) WHERE auth_user_id IS NOT NULL;
```

`auth_user_id` is null until the member's first login. On magic-link callback, the server action looks up `members` by email (already unique), sets `auth_user_id` to the new auth user's id, and stamps the session. Subsequent visits resolve via `auth_user_id`. No new "users" table — `members` stays the source of truth.

### 3.2 Companion link on `papers`

```sql
ALTER TABLE papers ADD COLUMN companion_url TEXT;
```

Set by `/wids-make-companion` to `/papers/<id>` (relative URL inside the app). Dashboard "your past meetings" links to it; emails link to it. Null until the companion is generated.

### 3.3 Helper function

Used by every RLS policy and by server components.

```sql
CREATE FUNCTION current_member_id() RETURNS INT
LANGUAGE SQL STABLE SECURITY DEFINER AS $$
  SELECT id FROM members WHERE auth_user_id = auth.uid()
$$;
```

### 3.4 Row-Level Security

Default-deny the four tables the portal touches, then narrow policies:

| Table | SELECT | INSERT | UPDATE | DELETE |
|---|---|---|---|---|
| `members` | All authenticated members can read `id, name, role` only | — | — | — |
| `meetings` | All authenticated members can read | — | — | — |
| `papers` | All authenticated members can read | — | — | — |
| `availability` | own rows (`member_id = current_member_id()`) | own rows | own rows | own rows |
| `meeting_attendance` | own rows | own rows | own rows | — |

Operator-side reads (slash commands, scheduled tasks) keep using the Supabase **service role key**, which bypasses RLS, so nothing on the operator side breaks.

The `availability` "submitted yet?" check is computed on every dashboard load:

```sql
SELECT EXISTS(
  SELECT 1 FROM availability
  WHERE meeting_id = $next_prep_meeting_id
    AND member_id = current_member_id()
);
```

`idx_availability_meeting` keeps this a single-index lookup.

### 3.5 `command_log` extension

The existing `command_log.source` CHECK constraint enumerates `('slash_command', 'scheduled_task')`. Extend by one value:

```sql
ALTER TABLE command_log DROP CONSTRAINT command_log_source_check;
ALTER TABLE command_log ADD CONSTRAINT command_log_source_check
  CHECK (source IN ('slash_command', 'scheduled_task', 'server_action'));
```

Every Next.js server action logs success/failure rows here so the operator's `/wids-status` can surface portal failures alongside slash-command failures.

## 4. Page-by-Page UX

Mobile-first responsive. Tailwind utility classes inline. No design system library — surface is too small to justify one.

### 4.1 `/` — Sign-in

One field (email), one button ("Send me a link"). On submit, calls Supabase `signInWithOtp({email, options: {emailRedirectTo: '/auth/callback'}})`.

If the email isn't in `members`, the server action returns "We don't have you on the roster — ask the operator to add you." Does **not** reveal whether the email exists in any other system (no enumeration). Otherwise: "Check your inbox."

### 4.2 `/auth/callback`

Standard Supabase magic-link handler: exchanges the token, creates a session, then runs a server action that links `members.auth_user_id = auth.uid()` if not already linked. Redirects to `/dashboard`.

### 4.3 `/dashboard` — home page after login

Single scrollable column on mobile, two columns on desktop. Sections, in order:

#### 4.3.1 Hero — Next meeting card

Pulls the most relevant upcoming meeting using this priority:

1. The `status='scheduled'` meeting with the earliest `scheduled_at` in the future.
2. Otherwise, the most recently created `status='prep'` meeting (`ORDER BY created_at DESC LIMIT 1`). The cycle alternation rule means at most one `prep` meeting should exist at a time, but this query is defensive against transient overlaps.
3. Otherwise: empty state — "No meetings scheduled yet. Sit tight."

All times displayed in **America/New_York** (the group's timezone). Stored as `TIMESTAMPTZ`, formatted client-side via `Intl.DateTimeFormat`.

Shows:
- Meeting type badge (`admin` / `reading_group`)
- Date + time (or "TBD" if `prep` with no `scheduled_at`)
- Location (or "TBD")
- Leader name (joined from `members`)
- Paper title (joined from `papers`)
- "Open paper companion" button if `papers.companion_url` is set
- **RSVP control** (only when `status='scheduled'`):
  - If member's `meeting_attendance.rsvp_status` is `no_response` (or no row exists): three buttons — `Attending` / `Tentative` / `Can't make it`
  - If already RSVP'd: shows current value with a "Change" link that re-reveals the buttons
  - Click writes to `meeting_attendance` (INSERT or UPDATE) with `responded_at = now()`. UI updates optimistically.

#### 4.3.2 Availability banner

Renders only if the current `prep`-status meeting exists and has no `availability` row for this member. Yellow background, "Submit your availability for [meeting type] meeting" CTA → `/availability`.

#### 4.3.3 Your stats

Three numbers:
- "Meetings attended" — count of `meeting_attendance` where `member_id` is mine, `rsvp_status='attending'`, and meeting `status='done'`
- "Papers led" — count of `meetings` where `leader_id` is mine and `status='done'`
- "Next month availability submitted: yes/no"

#### 4.3.4 Your history

A simple list (newest first), 10 items max with "Show more" link (loads next 10 client-side, no pagination URL state). Each row: paper title, date, "Open companion" link if `companion_url` is set.

No filters, no search, no archive UI beyond this. YAGNI.

### 4.4 `/availability` — submit availability for the next meeting in `prep`

Server-rendered with the meeting context loaded from `meetings`. Target meeting is selected with the same priority as the dashboard hero (§4.3.1) but restricted to `status='prep'` — i.e. the most recently created `prep` meeting (`ORDER BY created_at DESC LIMIT 1`).

Shows a calendar widget for the next 30 days; member taps days they can attend.

Each tapped day creates a row `(meeting_id, member_id, range_start = day 18:00 America/New_York, range_end = day 21:00 America/New_York)` — keeps the schema's existing range model, but the UI is just day-toggling, not time-picking. The 18:00–21:00 evening window is **hardcoded for v1** because all current group meetings happen in that window. If the group later wants per-meeting custom windows, that's an additive change to `meetings` (e.g., `default_start_hour`, `default_end_hour`) and one form field on `/availability`.

If they've already submitted, the page loads in "edit" mode with their previous selection pre-filled. Submit replaces (delete-then-insert in a transaction). Confirm modal before delete. After save, redirects to `/dashboard` with a flash message.

If there's no `prep` meeting at all, page shows "Nothing to schedule right now — check back when you get an email."

### 4.5 `/papers/<id>` — public companion page

Static-rendered at build time via `generateStaticParams` (which reads the directory listing of `/content/papers/`).

Layout:
- **Header**: paper title, authors, "Open notebook in Colab" button (top-right, sticky on scroll), link back to arxiv (`papers.url`)
- **Body**: scrollable single column. Each section from `/content/papers/<id>.json`:
  - Section heading
  - Markdown prose (~2–4 sentences, what this section of the paper does)
  - Mermaid diagram block (rendered client-side via `mermaid.js` lazy-imported only on this route)
  - "Run cell N in Colab ↗" link that jumps to that cell in the notebook (Colab supports `#scrollTo=` anchors)
- **Footer**: "This companion was generated for the WiDS NYC AI Reading Group on [date]. The paper itself is the source of truth."

No login. No tracking. Static content rendered fast.

## 5. `/wids-make-companion` Command Flow

Mirrors the existing `/wids-make-guide` 3-stage parallel-subagent pattern, but produces JSON + notebook instead of PDFs.

### 5.1 Inputs

`paper_id` (or defaults to the paper of the current `prep` meeting if omitted). Optional `--dry-run` flag (validate everything, print preview, do not commit).

### 5.2 Stage 1 — Section breakdown

Single subagent. Reads the paper PDF (`papers.pdf_drive_url`). Returns a list of 3–7 sections, each `{title, summary}`. Summary is 2–3 sentences explaining what this part of the paper does.

**Precondition check**: if `papers.pdf_drive_url` is null, the command aborts immediately with a message pointing the operator at `/wids-find-paper` to attach a PDF first. No subagent dispatch happens.

Subagent has explicit instructions: sections must be discussion-friendly chunks, not arbitrary slicing. Typical mapping:
1. Problem
2. Prior work / motivation
3–5. The technique broken down
6. Results
7. Limitations

Failure: returns <3 sections → abort, ask operator to retry (likely paper PDF unreadable).

### 5.3 Stage 2 — Per-section content

Parallel subagents, one per section. Each gets `{paper_pdf, section_title, section_summary}` and returns:

- **Mermaid diagram** — validated by parsing. Invalid → retry once with the parse error in the prompt. Still invalid → fall back to a single-node "see paper" diagram.
- **Python code cell** — runs in Colab free tier in <10 seconds, no GPU. Toy inputs only. Pedagogical, not realistic. Imports at the top of the cell. **Cells are self-contained** (each cell runnable in isolation, no shared global state) because Colab users skip around.

Failure: individual subagent fails twice → fall back to a stub (`# TODO: add example for this section`). Operator can regenerate that section after.

### 5.4 Stage 3 — Assemble + validate

Sequential, in the main agent:

- Stitch sections into `/content/papers/<id>.json`:
  ```json
  {
    "paper_id": 42,
    "title": "...",
    "generated_at": "2026-05-03T...",
    "sections": [
      { "title": "...", "summary": "...", "mermaid": "...", "code": "..." }
    ]
  }
  ```
- Build `/public/notebooks/<id>.ipynb`: one Markdown cell + one code cell per section, plus a top "Setup" markdown cell with the paper title and a single `pip install` cell with the union of pip imports detected across cells. JSON-validate against `nbformat` schema.
- Mermaid validation: invoke `@mermaid-js/parser` on every diagram. Any failure aborts with a clear error.

### 5.5 Human-in-the-loop review

After Stage 3 succeeds, the slash command:

1. Prints a section-by-section preview to the operator: section title, first ~80 chars of prose, "diagram: <N nodes/edges>", "code: <N lines>".
2. Offers: `[a] approve and publish`, `[r N] regenerate section N`, `[c] cancel and discard`.
3. Loops until approve or cancel.

### 5.6 Publish step

After approval:

```sh
git add content/papers/<id>.json public/notebooks/<id>.ipynb
git commit -m "companion: paper <id> — <title>"
git push
```

Then a single SQL update:

```sql
UPDATE papers SET companion_url = '/papers/' || $1 WHERE id = $1;
```

Vercel auto-deploys on push. Companion is live ~30 seconds later. Slash command tells operator the live URL.

### 5.7 Re-runs

Idempotent. Running `/wids-make-companion <id>` on a paper that already has a companion overwrites the JSON + ipynb and updates `papers.companion_url` again. Git history is the version history.

### 5.8 Failure → DB consistency

If git push fails, files are left staged, operator is told to resolve manually, and `papers.companion_url` is **not** updated. DB state and git state stay aligned: `companion_url IS NOT NULL` only when the corresponding files are pushed and live.

## 6. Integration With Existing System

### 6.1 Scheduled tasks that change

- **`cycle-keep-alive`** (currently emails Google Form link): emails the **portal URL** (`/availability`) to anyone in `members` who's `active` and has no `availability` row for the current `prep` meeting. Subject line and cadence unchanged.
- **`process-form`** (currently scrapes Google Form responses into `availability`): **deleted entirely.** Portal writes to `availability` directly via authenticated server actions. One fewer scheduled task, one fewer failure mode.
- **`form-response-chase`**: rename to **`availability-chase`** (logic unchanged — find members with no `availability` row, nudge them — but the nudge points to the portal, not the form).
- **`calendar-rsvp-sync`**: gain a tiebreaker. Only overwrites `meeting_attendance.rsvp_status` if the calendar event's response timestamp is **later than** the DB row's `responded_at`. Otherwise leaves the row alone. Last-write-wins, by timestamp. No bidirectional push.
- **`pre-meeting-reminder`**, **`leader-nudge`**, **`post-meeting-thanks`**, **`meeting-auto-advance`**: untouched.

### 6.2 Slash commands that change

- **`/wids-make-guide`**: unchanged. Companion is a separate command.
- **`/wids-status`** (operator dashboard): gains one line — "Companion published for current paper: yes/no" — read off `papers.companion_url`.
- **`/wids-send-packets`**: email body now includes a "Read the paper companion" link if `papers.companion_url` is set.
- **`/wids-bootstrap`**: unchanged. The first time a seeded member visits the portal and enters their email, magic link works because the email is already in `members`.

### 6.3 New slash command

- **`/wids-make-companion <paper_id>`** — see Section 5.

## 7. Testing Strategy

Three layers, in cost/value order. No test framework added.

### 7.1 RLS smoke test

Single SQL test file `tests/rls.sql`. Sets `auth.uid()` to a fake member's `auth_user_id`, then asserts:

- Can read own `availability` ✓
- Cannot read another member's `availability` ✗ (returns 0 rows)
- Cannot insert with a different `member_id` ✗ (raises)
- Can `UPDATE` own `meeting_attendance` ✓
- Cannot `UPDATE` another member's `meeting_attendance` ✗

Run manually before applying any schema migration via `supabase db execute < tests/rls.sql`.

### 7.2 Hand-tested end-to-end happy paths

Three flows, run by hand against a Vercel preview deploy:

1. Sign in via magic link → land on dashboard → see the right "next meeting" card with correct values.
2. Visit `/availability` → tap 5 days → submit → reload → those 5 days are pre-filled.
3. Visit `/papers/<id>` (anonymous) → all sections render, mermaid diagrams render, "Open in Colab" link opens a working notebook.

### 7.3 Companion generation dry-run

`/wids-make-companion <id> --dry-run` flag: runs Stages 1–3, validates Mermaid + nbformat, prints preview, **does not commit**. Run once per new paper before the real generate.

## 8. Rollout

One cycle of overlap, then cut over.

1. **Cycle N (current)**: ship the schema migration + the portal app behind a Vercel password. Operator + 1–2 willing members test it. `process-form` and `cycle-keep-alive` still use the Google Form. Both surfaces alive in parallel.
2. **End of Cycle N**: flip `cycle-keep-alive` to portal email, decommission `process-form`, remove the Vercel password, send all members a "the portal is live" email with their first magic link.
3. **Cycle N+1**: Google Form retired. `/wids-make-companion` ships with the next paper.

## 9. Operational Notes

- **Env vars** (Vercel project settings):
  - `NEXT_PUBLIC_SUPABASE_URL` — browser-safe
  - `NEXT_PUBLIC_SUPABASE_ANON_KEY` — browser-safe
  - `SUPABASE_SERVICE_ROLE_KEY` — server actions only, never sent to browser
- **Slash command secrets**: `/wids-make-companion` reads the same `SUPABASE_SERVICE_ROLE_KEY` from local `.env` (already present for existing slash commands).
- **Monitoring**: every server action logs to `command_log` with `source='server_action'`. Operator surfaces failures via `/wids-status` or direct SQL.
- **Cost**: Vercel Hobby + Supabase free tier. Well within limits for ~10 active members and a few hundred companion-page views per cycle.

## 10. Open Questions

None blocking implementation. The following are deferrable:

- Should `/papers/<id>` 404 if `papers.companion_url IS NULL` for a paper that exists in the DB? (Default: yes, since the static route only generates for papers that have a content JSON file. Visiting an un-generated paper id falls through to Next.js's 404 page.)
- Should the dashboard's "Your history" cap at 10 with a "Show more" button, or paginate with a URL query param? (Default: client-side "Show more" — keeps URL state simple. Revisit if any member has 50+ past meetings, which is years of cycles away.)
