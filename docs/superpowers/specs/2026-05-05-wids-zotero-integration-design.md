# Zotero / arxiv-sanity integration — design

**Status:** spec, awaiting review
**Owner:** Michelle Rojas
**Date:** 2026-05-05

## Goal

Give the WiDS NYC Reading Group two things, in two stages:

1. **A permanent, public bibliography of every paper the group has read** — hosted on zotero.org as a Zotero Group Library, with WiDS-specific context (meeting date, leader, topic, link to the companion page) attached to each entry.
2. **A discovery aid for the next leader** — when a member is picked to lead, surface candidate papers ranked by similarity to the group's past readings (an arxiv-sanity-style recommender).

This document specifies **stage 1 only** (the Zotero library of record). Stage 2 is described briefly at the end and gets its own follow-up spec.

## Decomposition

Stages 1 and 2 are independent:

- Stage 1 cares only about *what the group has read*; it doesn't care how a paper was picked.
- Stage 2 cares about *what the group should read next*; it doesn't care where the answer is stored.

They share zero code. Splitting them lets us ship a useful, finished thing (public bibliography) without blocking on the larger discovery design.

## Scope of stage 1

**In scope:**

- A new public Zotero Group Library for WiDS NYC.
- Automatic push of each newly-read paper at the moment its companion page is generated by `/wids-make-companion`.
- A child note attached to each Zotero item containing the WiDS context (meeting date, leader, topic, companion URL).
- Per-source metadata extraction (arXiv API, CrossRef API, fallback) so non-arXiv papers also get rich entries.
- A `/wids-zotero-retry <meeting-id>` slash command for re-running a failed push.

**Out of scope (this spec):**

- Pushing PDFs as Zotero attachments.
- Backfilling historical readings (~19 entries that pre-date the DB; deferred — see [Backfill](#backfill)).
- Any change to leader-picking, paper-picking, or companion-generation logic itself.
- The arxiv-sanity discovery feature (stage 2).
- Updating Zotero items if the underlying paper metadata in our DB changes after the initial push.

## High-level flow

```
operator runs /wids-make-companion <meeting-id>
   ↓ (existing) generate Mermaid + Colab notebook
   ↓ (existing) git stage + push
   ↓ (existing) UPDATE papers.companion_url
   ↓ (NEW) push to Zotero:
       1. read papers.zotero_item_key — if non-null, log "already pushed", done.
       2. extract metadata from papers.url:
            - arxiv.org/abs/...   → arXiv API
            - URL with DOI         → CrossRef API
            - other                → fallback to papers.{title, authors, year, venue}
       3. POST /groups/<group_id>/items to create Zotero item
       4. POST /groups/<group_id>/items to create child note (linked to item via parentItem)
       5. UPDATE papers SET zotero_item_key = <returned key>
   ↓ (existing) command_log row
```

The push is the last step before `command_log`, so a Zotero failure does not block the companion artifact from shipping.

## Data model

One column added to `papers`:

```sql
-- migrations/009_papers_zotero_item_key.sql
ALTER TABLE papers ADD COLUMN zotero_item_key TEXT;
COMMENT ON COLUMN papers.zotero_item_key IS
  'Zotero item key (8-char alphanumeric, e.g. "ABCD1234") for the WiDS NYC group library. NULL = not yet pushed. Set on first successful push by /wids-make-companion.';
```

No new tables. No `meetings` column — the child note lives on the Zotero side and is created together with the parent item; we don't need a local pointer to it.

**Edge case (rereads):** if the same paper is ever read in two different cycles, the second `/wids-make-companion` will see `zotero_item_key` already set and skip — no second item, no second note. The public bibliography will under-represent the rereading. This is accepted as a known minor wart; if it ever happens, the operator can add a second child note manually in Zotero's UI, or we move to a join-table model in a follow-up.

## Metadata extraction

Per the URL pattern on `papers.url`:

| URL pattern | Source | Returns |
|---|---|---|
| `^https?://arxiv\.org/abs/[^/]+$` (after normalization) | **arXiv API** — `https://export.arxiv.org/api/query?id_list=<id>` | title, authors, abstract, primary category, published date |
| URL contains a DOI, OR Zotero translator-server-style sites (MDPI, Nature, Springer, IEEE, ACM, OpenReview, Taylor & Francis) | **CrossRef API** — `https://api.crossref.org/works/<doi>` | title, authors, abstract, journal/venue, year, type, ISSN |
| Anything else (raw PDFs, university hosting, blog posts) | **DB fallback** — `papers.{title, authors, venue, year}` | whatever the operator put in |

**URL normalization** (do this before pattern-matching):

- `arxiv.org/pdf/<id>` → `arxiv.org/abs/<id>`
- Strip `?...` query strings on arxiv URLs
- Strip the `?needAccess=true` and similar params on tandfonline-style URLs
- Lowercase the scheme and host

**DOI extraction:** for non-arXiv URLs, attempt to find a DOI in this order:

1. **Pattern-match the URL itself** for `10\.\d{4,9}/[-._;()/:a-z0-9]+` (works for tandfonline `/doi/epdf/10.1080/...`, ACM `/doi/10.1145/...`, and any URL that already encodes its DOI in the path).
2. **If no DOI in the URL, fetch the page** and look for `<meta name="citation_doi" content="...">`. This is the [Highwire Press metadata standard](https://scholar.google.com/intl/en/scholar/inclusion.html#indexing) deployed by virtually every academic publisher (MDPI, Nature, Springer, Wiley, IEEE, ACM, OpenReview, etc.) — one HTTP GET, no auth, no scraping fragility. MDPI's `mdpi.com/2227-7390/13/10/1551` exposes `citation_doi=10.3390/math13101551` this way.
3. If neither finds a DOI: fall through to the DB-fallback path.

The page fetch in step 2 has a 5-second timeout; on timeout or non-200 we fall through to fallback rather than blocking the push.

**No translation-server.** Earlier drafts considered Zotero's translation-server. Rejected: there is no project process to colocate it with (Next.js + Supabase + scheduled-tasks MCP only), and there is no reliably-maintained public instance. arXiv API + CrossRef cover the common cases; the fallback handles the long tail.

## Zotero API usage

**Auth:** per-user API key + group ID. The key is the operator's personal Zotero key with library-write access to the WiDS NYC group.

**Endpoints used:**

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/groups/<group_id>/items` | Create the paper item |
| `POST` | `/groups/<group_id>/items` (with `parentItem` set) | Create the child note |

**Item types:**

- arXiv → `preprint` (Zotero item type added in v6; falls back to `journalArticle` for older clients but the API accepts `preprint`)
- CrossRef-resolved → whatever CrossRef's `type` maps to (`journalArticle`, `proceedings-article`, `book-chapter`)
- Fallback → `webpage`

**Group library visibility:** must be set to **public + closed membership** in Zotero's group settings (`zotero.org/groups/<group_id>/settings`). Public means anyone with the link can view; closed membership means only invited members can edit/add. Operator does this once during setup; out of scope for this code.

**Rate limits:** Zotero allows 60 requests per minute per key. Two requests per push (item + note) means up to 30 papers/min, which is wildly above the actual rate of ~2 papers/month. No backoff logic needed; if a 429 is ever returned, fall through to error handling.

## WiDS context note format

The child note attached to each Zotero item, in HTML (Zotero notes are HTML):

```html
<p><strong>WiDS NYC Reading Group</strong></p>
<ul>
  <li><strong>Meeting:</strong> {meeting_date_formatted}</li>
  <li><strong>Leader:</strong> {leader_name}</li>
  <li><strong>Topic:</strong> {topic_names_joined}</li>
  <li><strong>Companion:</strong> <a href="{companion_full_url}">{companion_full_url}</a></li>
</ul>
```

Where:

- `meeting_date_formatted` — e.g. `Wednesday, March 12, 2026` (from `meetings.scheduled_at` in the group's local time, America/New_York)
- `leader_name` — `members.name` for the meeting's `leader_id`
- `topic_names_joined` — `topics.name` joined with ` / ` for all topics linked via `paper_topics`
- `companion_full_url` — `https://<vercel-prod-host>{papers.companion_url}` (the URL on the deployed WiDS site; the prod host comes from a new env var, see [Configuration](#configuration))

If any of these are missing (e.g. `leader_id` is null, no topics linked), the line is omitted from the note rather than rendered as "Leader: None."

## Trigger integration

Edit [`.claude/commands/wids-make-companion.md`](.claude/commands/wids-make-companion.md) to add a new stage between the existing `UPDATE papers.companion_url` step and the `command_log` insert. The new stage runs the push in five sub-steps (see [High-level flow](#high-level-flow)).

The push code itself lives in **a new TypeScript module at `web/lib/zotero/push.ts`** with a CLI entry point at `web/scripts/zotero-push.ts` runnable via `npx tsx`. The slash command invokes it as:

```bash
ZOTERO_API_KEY=... ZOTERO_GROUP_ID=... \
  npx tsx web/scripts/zotero-push.ts --paper-id=<id> --meeting-id=<id>
```

Why TypeScript in `web/`: same Supabase client (`@supabase/supabase-js`) is already there, same node_modules, no new top-level directory. The script is not part of the Next.js bundle — it's a standalone tsx entry — but it shares dependencies.

## Idempotency

Single check, before any external API call:

```sql
SELECT zotero_item_key FROM papers WHERE id = :paper_id;
```

If non-null, log `"Zotero: paper <id> already at item <key>, skipping push"` and exit success. The `command_log` summary reflects "already in Zotero" rather than "pushed."

If null, do the push; on success do the `UPDATE papers SET zotero_item_key = ...`.

The update is the only DB write — there is no transaction needed. If the script crashes between the Zotero POST and the DB UPDATE, the next retry will see `zotero_item_key IS NULL` and create a duplicate. To prevent that:

- Before the Zotero POST, query the group's items for one with `extra` field containing `wids_paper_id:<id>` (we'll set this as a stable correlator on every item we create). If found, treat as "already pushed" and just record the existing key.
- This adds one extra GET per push but eliminates the dup-on-crash risk.

## Failure handling

**Soft fail with surfaced warning.** Any error during the push step (network, Zotero 4xx/5xx, CrossRef timeout) is caught, logged, and printed to the operator's CLI output:

```
⚠ Zotero push failed for paper 42: <error>
   Re-run with: /wids-zotero-retry 42
```

The `/wids-make-companion` overall outcome remains `success` in `command_log` (the companion artifact shipped); the Zotero failure is recorded as a separate `command_log` row with `status='failure'` and `name='/wids-make-companion:zotero-push'`.

**`/wids-zotero-retry` slash command** — new file `.claude/commands/wids-zotero-retry.md`. Takes a meeting ID. Looks up `meetings.paper_id`, then re-runs the push. Same idempotency check; same module.

## Configuration

Three new env vars, loaded by `web/scripts/zotero-push.ts`:

| Var | Source | Used for |
|---|---|---|
| `ZOTERO_API_KEY` | [zotero.org/settings/keys](https://www.zotero.org/settings/keys) | Authorization header on all Zotero API calls |
| `ZOTERO_GROUP_ID` | URL on the group's Zotero page (numeric) | Which group library to write to |
| `WIDS_PROD_HOST` | Vercel prod URL (e.g. `widsnyc.org` if a custom domain is set, else `wids-nyc-reading-group-assistant.vercel.app`) | Build the absolute companion URL for the note |

These go in the operator's local `.env` (slash-command runs are operator-side) and are listed in `web/.env.example`. They are *not* needed by `scheduled_tasks/` — none of the scheduled jobs touch Zotero in this spec.

CrossRef and arXiv APIs require no auth.

## Backfill

**Deferred from this spec.** Approximately 19 historical readings exist before the Supabase DB was created; they live in past Gmail threads and a Google Doc.

A separate Cowork session has already produced a clean CSV of those readings at [`docs/superpowers/specs/wids-zotero-historical-readings.csv`](docs/superpowers/specs/wids-zotero-historical-readings.csv). Columns: `meeting_date`, `paper_title`, `paper_url`, `leader_name`, `topic_name`, `_notes`.

Once stage 1 forward-going is shipped, a small follow-up adds:

- A `--from-csv <path>` mode to `web/scripts/zotero-push.ts` that reads the CSV and pushes each row, looking up `member_id` by name and creating items + notes without requiring a `papers` row.
- The historical entries get a slightly different note (no companion URL — these never had companion pages).

This work is *not* in stage 1 because it changes the script's interface and adds CSV parsing, member-name lookup, and a special-case "no companion link" template — all of which can be designed and reviewed cleanly once the forward-going path is proven.

## Stage 2 (deferred): arxiv-sanity discovery

Brief pointer for a future spec, NOT part of this implementation:

When a member is picked as next leader, `/wids-find-paper` could surface ranked candidate papers from arXiv, scored by similarity to the group's past readings. Approximation rather than self-hosting arxiv-sanity-lite: TF-IDF or embedding similarity over the existing `papers` table against new arXiv submissions in the group's primary categories (cs.LG, stat.ML, etc.). Likely 200–400 lines, no new infra.

This will be its own design doc, brainstormed when the operator is ready.

## Out of scope / explicit non-goals

- **PDF attachment uploads** — companion pages already serve as the canonical artifact location; Zotero entries link out, they don't archive.
- **Two-way sync** — Zotero is write-only from our side. If someone edits a Zotero item, our DB doesn't learn about it.
- **Update on metadata change** — if a paper's `papers.title` or `papers.url` is corrected after the initial push, the Zotero item is not updated. Operator can edit in Zotero's UI.
- **Reread handling** — see [Data model](#data-model) edge case.
- **Cancelled meetings** — if a meeting is cancelled after `/wids-make-companion` ran, the Zotero item stays. Operator deletes manually in Zotero.

## Testing

- **Unit tests** in `tests/zotero/` covering URL normalization, source classification (arxiv vs DOI vs fallback), DOI extraction, and the note HTML template.
- **Integration test** with mocked HTTP layer: full flow from a `paper_id` through to the two POST bodies sent to Zotero, asserting the exact payloads for an arXiv example, an MDPI example, and a fallback example.
- **No end-to-end test against real Zotero.** A one-time manual run during PR review (operator pushes a real paper to a personal test group library, verifies the entry, then deletes it) covers the live-API leg.

## Open questions / verification before implementation

1. **Zotero group library not yet created.** Operator action: create a new public group library at zotero.org named "WiDS NYC Reading Group" (closed membership) and capture the group ID for `ZOTERO_GROUP_ID`. Out of scope for the code; needs to happen before the first push.
2. **`papers.url` content for historical entries** in the backfill CSV varies in format (some `/abs/`, some `/pdf/`, some `?needAccess=true`). The normalization rules in [Metadata extraction](#metadata-extraction) cover the cases observed; a backfill dry-run will confirm.
3. **Vercel prod host for `WIDS_PROD_HOST`.** Confirm whether a custom domain is set (and use that) or the default vercel.app subdomain.

## Risks

- **Zotero API key in operator env** — same trust model as Supabase service-role key; operator's machine. No new exposure.
- **CrossRef API quality varies** — some publishers (especially older articles) have thin or wrong metadata in CrossRef. The fallback to `papers.{title, authors}` catches this; we always have those locally.
- **arXiv ID extraction** — some old arXiv URLs use `arxiv.org/abs/cs.LG/0601001`-style category-qualified IDs. The normalization regex needs to handle both forms; called out as a unit-test case.
