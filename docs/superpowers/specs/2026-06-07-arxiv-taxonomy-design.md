# arXiv Category Taxonomy — Design

**Date:** 2026-06-07
**Status:** Approved (design)
**Source page:** <https://arxiv.org/category_taxonomy>

## Goal

Build a canonical, structured arXiv category taxonomy (code → human-readable
name, e.g. `cs.LG` → "Machine Learning") and wire it into three paper-discovery
surfaces of `/wids-find-paper`:

1. `search` sub-mode — scope arXiv discovery to chosen categories.
2. `pick` auto-tagging — enrich topic tagging with the paper's arXiv categories.
3. Web `/admin/suggest` — a "browse arXiv by category" discovery helper.

The taxonomy is the shared foundation; the three integrations are consumers.

## Non-goals

- No live/runtime fetching of the taxonomy in discovery flows (it changes a few
  times a year; a snapshot is sufficient).
- No new DB schema in this work (pick integration is enrich-only — see §4.3).
- No full arXiv-listing/browse integration in the web app (the web piece is a
  link-out helper, not an in-app search — see §4.4).

## Architecture overview

```
arxiv.org/category_taxonomy
        │  (manual run)
        ▼
scripts/build_arxiv_taxonomy.py  ──writes──►  data/arxiv-taxonomy.json  (canonical)
        │                                              │
        └──────────────also writes────────────────────┴──►  web/lib/arxiv/taxonomy.ts (generated)

Consumers:
  data/arxiv-taxonomy.json   →  wids-find-paper.md  (search validation, pick enrichment)
  web/lib/arxiv/taxonomy.ts  →  SuggestForm.tsx     (browse-by-category helper)
```

## 1. Canonical data file — `data/arxiv-taxonomy.json`

Single source of truth. Language-agnostic so the agent (reading the slash
command), the Python helper, and the web app can all consume it.

```json
{
  "generated_at": "2026-06-07",
  "source": "https://arxiv.org/category_taxonomy",
  "categories": [
    {
      "code": "cs.LG",
      "name": "Machine Learning",
      "description": "Papers on all aspects of machine learning research ...",
      "group": "Computer Science",
      "relevant": true
    }
  ]
}
```

Field contract:

| Field          | Type    | Notes |
|----------------|---------|-------|
| `code`         | string  | e.g. `cs.LG`, `stat.ML`, `math.AG`. Unique key. |
| `name`         | string  | Human-readable label from the parenthetical. |
| `description`  | string  | The category description paragraph (may be `""` if absent). |
| `group`        | string  | Top-level group, e.g. `Computer Science`. |
| `relevant`     | boolean | `true` for WiDS-relevant archives (see §1.1). |

`categories` is a flat array (not nested by group) — flat is easier for every
consumer to filter; `group` is carried on each row for grouping when needed.
Sorted by `code` for stable diffs.

### 1.1 Relevance rule

`relevant = true` when the archive prefix (the part before the first `.`, or the
whole code for dotless archives) is in:

```
cs, stat, math, eess, econ, q-bio, q-fin
```

Everything else (all `physics`-group archives, etc.) is `relevant = false`. The
set lives as a documented constant `RELEVANT_ARCHIVES` in the build script. This
is archive-level (coarse) on purpose — defensible and low-maintenance; no
per-category hand-curation.

## 2. Generated TS module — `web/lib/arxiv/taxonomy.ts`

Generated by the build script from the JSON. Never hand-edited (header comment
says so). Shape:

```ts
// AUTO-GENERATED by scripts/build_arxiv_taxonomy.py — do not edit by hand.
export interface ArxivCategory {
  code: string;
  name: string;
  description: string;
  group: string;
  relevant: boolean;
}

export const ARXIV_TAXONOMY: readonly ArxivCategory[] = [ /* ... */ ];

export const RELEVANT_CATEGORIES: readonly ArxivCategory[] =
  ARXIV_TAXONOMY.filter(c => c.relevant);
```

## 3. Build script — `scripts/build_arxiv_taxonomy.py`

Run via uv: `uv run --with httpx --with beautifulsoup4 scripts/build_arxiv_taxonomy.py`.

Responsibilities:

1. Fetch `https://arxiv.org/category_taxonomy` (httpx, 15s timeout).
2. Parse the DOM:
   - Top-level groups are `<h2>` headers (e.g. "Computer Science").
   - Each category is an `<h4>` whose text is `cs.AI (Artificial Intelligence)`
     — code is the leading token, name is inside the parentheses.
   - The description is the sibling `<p>` following the `<h4>` (may be empty).
3. Apply the relevance rule (§1.1).
4. Write `data/arxiv-taxonomy.json` (sorted by `code`, 2-space indent).
5. Write `web/lib/arxiv/taxonomy.ts` from the same in-memory data.

Design points:

- **Pure parse function** `parse_taxonomy(html: str) -> list[Category]` separated
  from I/O, so it can be unit-tested against a saved fixture with no network.
- **Sanity guard:** if fewer than ~100 categories or zero relevant categories are
  parsed, exit non-zero with a clear message (page structure likely changed).
- `generated_at` is passed in / stamped at run time (kept out of the pure parse
  function so tests are deterministic).

## 4. Integrations

### 4.1 `search` sub-mode (`.claude/commands/wids-find-paper.md`, Step 2)

Add an optional, repeatable `--category <code>` argument.

- **Validation:** each supplied code is checked against `data/arxiv-taxonomy.json`.
  Unknown code → halt with: `"Unknown arXiv category '<code>'. See data/arxiv-taxonomy.json for valid codes."` (typo/hallucination guard — the data file's validation role).
- **When categories are present:** discovery uses the arXiv **export API** instead
  of scraping the HTML search page:
  `http://export.arxiv.org/api/query?search_query=%28cat:cs.LG+OR+cat:stat.ML%29+AND+all:<encoded_query>&start=0&max_results=5`
  The response is Atom XML — parse `<entry>` elements for title, authors, summary
  (abstract), arXiv id, published year. This is markedly more stable than the
  current HTML scrape.

  **URL-encoding contract (confirmed against the arXiv API user manual):** the
  `search_query` value is raw query syntax, so reserved characters must be
  percent-encoded by hand — spaces → `+`, boolean operators → `+AND+` / `+OR+` /
  `+ANDNOT+`, grouping parentheses → `%28` / `%29`, phrase quotes → `%22`. The
  `<encoded_query>` term must itself be URL-encoded. A single category needs no
  parentheses (`search_query=cat:cs.LG+AND+all:<encoded_query>`); multiple
  categories are OR-grouped inside `%28…%29` as shown above. Verbatim doc example
  confirming the grouping encoding:
  `search_query=au:del_maestro+ANDNOT+%28ti:checkerboard+OR+ti:Pyrochlore%29`.
- **When no category is given:** behavior is unchanged (current HTML `/search/`
  flow), but the command prints a one-line hint listing the relevant-subset codes
  so the leader knows the option exists.
- Steps 2c–2e (insert candidates, assessments, present) are unchanged.

Argument-hint line at the top of the command is updated to document `--category`.

### 4.2 `pick` auto-tagging (Step 4d.5)

Today 4d.5 asks Claude to pick 0–3 topics from the `topics` table given the
paper's title + abstract. Enrich it:

- When `papers.url` is an arXiv URL, fetch the paper's metadata from the arXiv
  export API and read its `<category>` terms (primary + cross-list).
- Map each code → human name via the taxonomy. Codes not in the taxonomy are
  dropped (forward-compatible against a stale snapshot).
- **Inject the labels into the existing topic-tagging prompt** as a hint line:
  `"arXiv classifies this paper under: Machine Learning (cs.LG), Computation and Language (cs.CL)."`
  This biases topic selection without changing the topic vocabulary or output
  contract (still returns existing topic names only).
- Append the category labels to the Step 4e `command_log` summary:
  `"... arXiv categories: cs.LG, cs.CL"`.
- **No schema change.** If the paper is not on arXiv, or the API call fails, skip
  the enrichment silently and run 4d.5 exactly as today (graceful degradation).

### 4.3 No migration

Persisting arXiv categories to `papers` (a `text[]` column) was considered and
deferred (YAGNI). The enrich-only path delivers the user value (better tagging +
audit trail) with zero schema risk. Documented here so a future contributor knows
it was a deliberate choice, not an oversight.

### 4.4 Web `/admin/suggest` helper (`web/app/admin/suggest/SuggestForm.tsx`)

The suggest page is a *ranking* tool (paste candidate IDs → rank against past
picks); it has no arXiv search step. So the taxonomy is wired in as a
**discovery helper**, not a filter:

- A "Browse arXiv by category" section above the candidate textarea.
- A `<select>` populated from `RELEVANT_CATEGORIES` by default, with a
  "Show all categories" checkbox that swaps in the full `ARXIV_TAXONOMY`.
- Options labeled `cs.LG — Machine Learning`, grouped by `group` via `<optgroup>`.
- On selection, render a link to `https://arxiv.org/list/<code>/recent`
  (opens in a new tab) so the leader can browse recent papers in that category
  and copy candidate IDs into the existing textarea.
- Pure client-side; consumes the generated TS module; **no route/API changes.**

## 5. Testing

- **`tests/build_arxiv_taxonomy_test.py`** — unit tests for `parse_taxonomy`
  against a saved HTML fixture (`tests/fixtures/arxiv_taxonomy.html`, no network):
  - Known pairs resolve: `cs.AI` → "Artificial Intelligence", `stat.ML` →
    "Machine Learning", `math.AG` → "Algebraic Geometry".
  - Relevance flag: `cs.LG`/`stat.ML` true; a `physics`/`astro-ph` category false.
  - JSON schema: every row has all five fields with correct types.
  - Sanity: parsed count within an expected band (≥ 100).
- **`web/lib/arxiv/__tests__/taxonomy.test.ts`** — sync + invariants:
  - The TS `ARXIV_TAXONOMY` deep-equals the canonical JSON (drift guard).
  - `RELEVANT_CATEGORIES` is non-empty and a strict subset of `ARXIV_TAXONOMY`.
- **Slash-command changes** are markdown (no unit harness). A short smoke-test
  note is added to the spec follow-up: run `/wids-find-paper search "diffusion"
  --category cs.LG` against a scratch reading_group and confirm export-API parsing.

## 6. Build order

1. Foundation: build script + `data/arxiv-taxonomy.json` + `web/lib/arxiv/taxonomy.ts` + both tests.
2. `search` integration (4.1).
3. `pick` integration (4.2).
4. Web helper (4.4).

Each step depends only on step 1, so 2–4 are independent once the foundation lands.

## 7. Open risks

- **arXiv page structure drift** breaks the parser. Mitigated by the §3 sanity
  guard and the fixture test; re-running the script is the fix.
- **export API category-filter syntax** — confirmed against the arXiv API user
  manual (2026-06-07). The `cat:` field, `%28…%29` OR-grouping, and `+AND+`/`+OR+`
  operator encoding are documented and used in §4.1. No longer an open risk;
  retained here as the provenance for the §4.1 encoding contract.
