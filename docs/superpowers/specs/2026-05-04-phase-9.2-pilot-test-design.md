## Deliverables

Three artifacts. No app code touched.

### 1. `tests/pilot_test.py` — Python script for brittle steps

Run via `uv run tests/pilot_test.py <subcommand>` — no venv, no `pip install`. Dependencies declared inline with [PEP 723](https://peps.python.org/pep-0723/) script metadata so `uv` resolves them on the fly:

```python
# /// script
# requires-python = ">=3.11"
# dependencies = ["psycopg[binary]>=3.2"]
# ///
```

`psycopg` for flip/revert SQL (single dep, parameter binding, easy row counts). `rls` shells out to `psql` because `tests/rls.sql` uses psql-specific `\set` and `\gset` metacommands that no Python driver replays.

Three subcommands, dispatched via `argparse` (subparsers: `flip-rsvp`, `revert-rsvp`, `rls`).

**Config / env loading:**
- A small `@dataclass` `Env` holds the resolved values (`db_url`, `meeting_id`). Single instance built once per run by a `load_env()` helper that merges `web/.env.local` with `os.environ` (process env wins on conflict, so a shell `export` always overrides the file).
- `meeting_id` defaults to `6` (the current operator-DB target) but `Env` keeps it as a field rather than a module-level constant so a future replay can override via env var or CLI flag without code changes.
- All three subcommands need `SUPABASE_DB_URL` (full postgres connection string) **or** standard `PG*` vars. (Using the DB URL with service-role-equivalent superuser access for flip/revert means we don't need the Supabase HTTP API at all — one auth mechanism for the whole script.)
- `load_env()` fails loud with a one-line error naming the missing var.

**`flip-rsvp` subcommand:**
1. `SELECT id, type, status, scheduled_at FROM meetings WHERE id = %s` (param: `env.meeting_id`).
2. If `status='scheduled'`: print `meeting #6 already scheduled (scheduled_at=<x>); no-op` and exit 0. (Idempotent.)
3. If `type != 'reading_group'`: print `meeting #6 is not a reading_group meeting; aborting` and exit 1. (Guard against silent damage on a future replay against a different DB.)
4. `UPDATE meetings SET status='scheduled', scheduled_at = now() + interval '1 hour' WHERE id = %s`.
5. Print confirmation with the new `scheduled_at`.

**`revert-rsvp` subcommand:**
1. `SELECT status, scheduled_at FROM meetings WHERE id = %s`.
2. If `status='prep' AND scheduled_at IS NULL`: print `meeting #6 already at starting state; no-op` and exit 0. (Idempotent.)
3. `UPDATE meetings SET status='prep', scheduled_at=NULL WHERE id = %s`.
4. `DELETE FROM meeting_attendance WHERE meeting_id = %s`. Print `cleared N attendance rows` using `cur.rowcount`. (Otherwise leftover RSVP data confuses the operator on later cycle runs.)
5. Print confirmation.

**`rls` subcommand:**
- Wraps `psql -v ON_ERROR_STOP=1 -f tests/rls.sql` against `env.db_url` via `subprocess.run(..., check=False)`. Stream stdout/stderr through. Exit with psql's return code.
- The wrapper exists so the operator doesn't have to remember `ON_ERROR_STOP=1` and so env-var resolution lives in one place alongside flip/revert.

**Why default meeting ID = 6:**
- 9.2 is a one-time operator session; hand-rolled identity is fine.
- The `type='reading_group'` guard in `flip-rsvp` makes a future replay against a different DB self-checking rather than silently destructive.
- The value lives on the `Env` dataclass (not a module-level constant), so V2 backup operator can override via env var or CLI flag without editing the script.

**Why three separate subcommands instead of one auto-revert script:**
The operator-clicks-around step happens *between* flip and revert, and there's no clean way to pause a script mid-run for a human. The safety belt is convention: revert is the literal next step in the runbook after the manual click-through completes. Each subcommand is idempotent, so re-running is safe.

### 2. `docs/superpowers/runbooks/2026-05-04-phase-9.2-pilot-test.md` — execution runbook

**Step structure:**

```

4. Availability flow
   - Visit /availability. Tap 5 days. Submit.

   - Capture screenshot of saved state.

   - Click Colab link, confirm new-tab opens to a notebook.
```

**Failure handling:** if any step fails — pause, debug, fix, re-run from that step. flip/revert are idempotent so re-runs are safe.

**Screenshots:** captured for the operator's reference during the run. Not committed to the repo. The log entry's prose notes are the durable record.

**Edge cases called out in the runbook:**
- **SMTP rate limit (2 magic-links/hour/project):** if step 3 hits it, wait an hour or use the cookie-injection workaround documented in `reference_supabase.md`. We don't bake the workaround into 9.2 — it's a debugging aid, not a test.
- **Forgotten revert (step 8):** worst case is meeting #6 sits at `status='scheduled'` until the next `/wids-schedule-reading-group` run, which overwrites it anyway. Annoying, not destructive. Step ordering puts revert before the log append so the operator can't write the log without first reverting.

## Why the runbook adjusts the plan checklist

Plan §9.2 has 5 steps assuming a fresh-from-scratch deploy. Reality has shifted:

| Plan step | Plan assertion | Runbook adjustment |
| --- | --- | --- |
| Magic-link sign-in | "card shows correct next meeting" | "dashboard renders empty state (no scheduled meeting)" |
| Availability | works as written | unchanged |
| Companion | `/papers/test` or real id | `/papers/2` (only paper with companion content) |
| RSVP | "if a `status='scheduled'` meeting exists" | flip meeting #6 to scheduled via script, run RSVP, revert |
| RLS smoke | re-run `tests/rls.sql` | unchanged (subcommand is just a wrapper) |

Net effect: the runbook covers strictly more than the plan — both empty-state and populated-state dashboard renders, and three RSVP transitions instead of one.
